# Ferlab-Ste-Justine/cnv-post-processing: Changelog

and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## Unreleased

### `Changed`

- Each per-sample call's ID is now kept in `FORMAT/OID` (set in `NORMALIZE_CNV`, `:` percent-encoded as `%3A`), so every family-level VCF still names each sample's own original call after the truvari collapses keep one `ID` per cluster. Joint-called (`caller=DRAGEN_JOINT`) VCFs don't get it: they skip the collapses (see `docs/journal.md`)
- New `JOIN_PROBAND_CNV` step after slivar: for each proband (the PED's affected children), `slivar/<familyId>.<proband>.cnv.proband.vcf.gz` holds the proband's own calls from its input VCF (own `ID`, coordinates, `QUAL`, `FILTER`, `INFO`), joined through `FORMAT/OID` to the slivar records they're in, with those records' slivar tags, VEP annotations and family `FORMAT`. `INFO/COHORT_ID`, `COHORT_POS` and `COHORT_END` name the slivar record
- Family-mode Exomiser now runs after `JOIN_PROBAND_CNV`, on the proband VCF of the child the `familyPheno` phenopacket names (`proband.subject.id`): it scores the proband's own calls and intervals instead of the truvari-kept call, often a parent's, and its reports are named `<familyId>.<proband>.exomiser.*` (were `<familyId>.exomiser.*`). Families with no proband VCF (`DRAGEN_JOINT`, no `familyPed`, or a phenopacket proband who isn't a sequenced affected PED child) still run on the family VCF, under the old names; `--exomiser_start_from_vep` now only applies to them
- Pipeline version bumped to 2.0.0 (`manifest.version`, `.nf-core.yml`)
- Local-module software version collection moved to Nextflow topic channels (`topic: versions`, collated via `channel.topic("versions")`); only the pinned nf-core VEP components are still mixed into `ch_versions` manually
- CI Nextflow matrix is now 24.10.5 and 25.10.4, plus a non-blocking `latest-everything` canary in the nf-test workflow
- CI: every GitHub Action is pinned to a full commit SHA (release tag in a trailing comment), reusing Post-processing-Pipeline's SHAs where it pins the same action; `commit_lint.yml`'s `actions/checkout` moved from v2 to v4.2.2 in the process. The lint job is also pinned to Nextflow 24.10.5 instead of whatever release is latest
- [#XXX](https://github.com/Ferlab-Ste-Justine/cnv-post-processing/pull/XXX) BIOINFO-232: `EXOMISER` (and its `EXOMISER_SINGLE` alias) now uses the official `docker.io/exomiser/exomiser-cli:14.0.0-bash` image instead of the custom `ferlabcrsj/exomiser:2.8.1` one. The exomiser version reported in `versions.yml` is now read from the image's `exomiser-core` jar filename instead of a baked-in `/EXOMISER_VERSION.txt`, and the image's `/bin/bash` entrypoint is cleared for both processes in the `docker` and `podman` profiles.
- CI workflows harmonized with Post-processing-Pipeline: `ci-nf-test.yml` is replaced by nf-core's sharded `nf-test.yml` (affected tests split into up to 2 shards, a single `confirm-pass` result, full suite on releases and manual runs), `ci.yml` is renamed `ci-full-run.yml`, `linting.yml` now matches the reference (Python 3.13, PR and release triggers, `--release` lint only on PRs to `main`), and the S3 test-data download moved into the `.github/actions/copy-test-data` composite action. `.nf-core.yml` pins nf-core tools 4.1.0
- CI: new `ci-pr-title-lint.yml` checks that PR titles follow `<type>: <TICKET-123> <description>` (from Post-processing-Pipeline). `commit_lint.yml` stays for now; its removal is pending repository-setting changes, see `docs/journal.md`
- slivar mode-of-inheritance rules rewritten as a table (`assets/cnv-slivar-functions.js`): one call per affected child and record (`cnv_moi`), and, as in the SNV pipeline, one `--family-expr` per tag (`has_moi_call`) that tags the family with each of its children's calls, valued with its affected members; the calls are `denovo`, `denovo_suspect`, `inherited_maternal`, `inherited_paternal`, `recessive`, `recessive_lowconf`, `possible_denovo`, `possible_inherited_maternal`, `possible_inherited_paternal`, `inheritance_unresolved`, `mendelian_inconsistent` and `unknown_cn`, with X-linked names on non-PAR chrX (`x_linked_denovo`, `x_linked_recessive`). The call looks at the child and its parents only: there is no family-level tag, and who is affected elsewhere in the family is left to the reader (see `docs/journal.md`). These replace `de_novo_candidate`, `dominant_inherited`, `recessive_candidate`, `candidate` and `ambiguous`. Expected copy number is chromosome- and sex-aware (GRCh38 PARs; records crossing a PAR boundary, and chrM, aren't modelled), and parent of origin (`po_mother`, `po_father`, `po_both`, `po_ambiguous`, plus `po_denovo` and `po_possible_denovo`, SNV-style) is computed per sample (`--sample-expr`) by the same transmission rules the MoI tags use, for every child. Tested by `assets/cnv-slivar-moi-harness.js` against a golden file of named scenarios (`assets/moi_scenarios.expected.tsv`), which replaces `assets/tests/cnv_slivar_functions.test.js`
- CI: new `ci-slivar-harness.yml` runs the slivar rules harness on every PR and push to `main`, and fails if the committed scenario files are out of date
- The pipeline now stops at startup when a family has a `familyPed` and `vep_genome` isn't `GRCh38`, since slivar's chrX/chrY model uses GRCh38 PAR coordinates
- slivar parent-of-origin tags renamed: INFO `parent_of_origin_maternal`/`parent_of_origin_paternal`/`parent_of_origin_ambiguous` are now `po_mother`/`po_father`/`po_ambiguous`, and their functions in `assets/cnv-slivar-functions.js` (`moi_cnv_po_maternal`/`moi_cnv_po_paternal`/`moi_cnv_po_ambiguous`) carry the same names. Update any downstream filter on the old INFO keys
- slivar: a parent who is in the VCF but has no usable CN now counts as absent, as the SNV pipeline and Radiant treat a parent's no-call, so the child is called like a duo (e.g. kid CN 1, mother CN 2, father CN missing: `possible_denovo` instead of `unknown_cn`). `unknown_cn` is kept for a child without CN, or a carrier none of whose needed parents has a CN
- slivar: two parent-of-origin tags from the SNV pipeline, `po_possible_mother` and `po_possible_father`, for a child with one parent unknown (absent, or no CN) whose other parent carries a CNV it may have passed (duo D1: kid CN 1, mother CN 1). When that parent surely passed it, the child gets `po_mother` / `po_father` (duo D2: kid CN 0, mother CN 1), as in the SNV pipeline and Radiant. Before, these children got no parent-of-origin tag
- slivar: the de novo mode-of-inheritance tags are spelled `denovo`, like the parent-of-origin tags (`po_denovo`): `denovo`, `denovo_suspect`, `possible_denovo`, `x_linked_recessive_denovo`, `x_linked_dominant_denovo` (were `de_novo`, `de_novo_suspect`, `possible_de_novo`, `x_linked_recessive_de_novo`, `x_linked_dominant_de_novo` on this branch). The two X-linked names are no longer Radiant's `transmission_mode` values verbatim (see `docs/journal.md`)
- slivar: the mode-of-inheritance call and the parent of origin now come from one computation and one `TRIO_TABLE` row: every way one copy from each parent can add up to the child's CN, each copy named normal or a hit. The parent labels (`same`, `half`) are gone, and with them the cases where the call said `inheritance_unresolved` while the parent of origin was known: a child with a parent homozygous for a deletion (CN 0) is now `recessive` (trio), `inherited_*` or `recessive_lowconf` (duo); 139 records of the real NA12878 trio change that way. A duo whose known parent carries a different CNV but passed its normal copy is `possible_denovo` (was `inheritance_unresolved`), and a missing parent now passes 0, 1 or 2 copies, like a real one (kid CN 4, mother CN 3, no father: `po_mother`, was `po_possible_mother`)
- slivar: on non-PAR chrX, a de novo CNV is `x_linked_denovo` for a son or a daughter (was `x_linked_recessive_denovo` / `x_linked_dominant_denovo` on this branch), and a son's CNV inherited from his mother keeps `inherited_maternal` (was `x_linked_recessive`). `x_linked_recessive` is now only a daughter with both X copies hit. The SNV pipeline's names read dominant or recessive off the zygosity and who is affected: they don't fit a son's gain (CN 2: his normal X plus an extra copy), and the calls don't look at who is affected. 14 mode-of-inheritance tags instead of 15 (see `docs/journal.md`)
- **Breaking:** The pipeline now checks each family's PED against the sample names in the family VCF before the slivar step (ported from snv-post-processing BIOINFO-240), and stops with a message naming the problem and its fix if (1) a VCF sample has no PED row, or (2) a sequenced sample's father or mother is named but isn't in the VCF. slivar exits normally in both cases. In the first it left the sample out of the family, and a PED matching none of the VCF's names gave no tags at all. In the second, when the absent parent was the father, slivar also dropped the child's link to the mother, so the child silently got no mode-of-inheritance or parent-of-origin tag. PEDs that named unsequenced parents and ran before now fail; set those parents to `0`. Rows for relatives who weren't sequenced are still allowed. The new `--skip_ped_validation` parameter (default `false`) turns these errors into warnings and lets the run continue, e.g. for tests. See `validatePedAgainstVcf()` and `vcfSampleNames()` in `subworkflows/local/utils_nfcore_cnv_post_processing_pipeline/main.nf`, both with nf-tests. `docs/usage.md` now also says the PED uses the VCFs' sample names, not the samplesheet's `sample` column

### `Fixed`

- Depth refinement now sets `FORMAT/CN` to the expected copy number when it resolves a missing genotype to hom-ref. It only rewrote GT before, and slivar reads CN, so a depth-confirmed normal sample was still unknown to it: on the full-genome NA12878 trio, 656 of 1212 records were tagged `unknown_cn`, and with parents' CN missing `denovo` could never fire. The expected CN is the slivar rules' (2 on autosomes and PAR; non-PAR chrX 1 for a male, 2 for a female; non-PAR chrY 1 for a male), the depth band is scaled by it (a normal male's chrX reads about 0.5 and was almost never resolved: 15 more of NA12891's chrX genotypes now are), and a male's non-PAR chrX/chrY gets a haploid `0`. Sex comes from the family's PED, now passed to `DEPTH_GENOTYPE_REFINE`; without one, non-PAR chrX/chrY genotypes stay missing (before, they were checked against the autosomal band). chrM and records crossing a PAR boundary are no longer refined. Records under 5 kb aren't refined either (`ext.min_size`, default 5000): depth there can't tell a normal parent from a one-copy loss the caller missed, and on the full-genome NA12878 trio 16 of the 28 `denovo` calls refinement produced were parents' losses DRAGEN's joint caller found, 13 of them under 5 kb
- The cohort truvari collapse no longer drops a sample's call when it folds it into another sample's: truvari only copies an absorbed call's `FORMAT` when it reads its GT as set, which DRAGEN's `./1` (gain of unknown zygosity) and haploid `1` (e.g. a male's chrX) aren't, so the sample was left with no `GT`, `CN` or `OID` there, and slivar tagged it `unknown_cn` (36 calls of the full-genome NA12878 trio, 9 of them NA12878's). The new `RESTORE_COLLAPSED_FORMAT` step (`bin/restore_collapsed_format.py`) copies them back from truvari's removed VCF
- A family's merged VCF now always lists its samples in name order. Before, `BCFTOOLS_MERGE` got the per-sample VCFs in whatever order their tasks finished, so the sample columns of the family VCF, and of every file built from it, could change from one run to the next, and `-resume` could re-run the merge and every family-level step after it
- `conf/modules.config`'s VEP `ext.args` no longer fails to parse under Nextflow's strict config syntax (the default from 26.04, "Variable declarations cannot be mixed with config statements"); its local variables now live inside an `ext.args` closure. Resolved args are unchanged for all three cache flavors
